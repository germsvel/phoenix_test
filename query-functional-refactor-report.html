Making PhoenixTest.Query functional

Assessment only — no library code was changed. The goal is to remove Query’s explicit raising (!) API: Query returns data or structured failures, while Live, Static, Elements, and Assertions decide how to compose and raise user-facing errors. LazyHTML exceptions remain outside this scope.

Conclusion

This is feasible, but it is a contract refactor rather than a mechanical removal of raise. Query already has useful non-bang finders, but their result shapes differ by query type and one supposedly non-bang label path raises. The first required change is a single, lossless result/failure contract. Once that exists, every outer layer can render its own error without re-querying or losing candidates.

The clean dependency direction is:

Live / Static / Element actions / Assertions
                 │  call and interpret
                 ▼
Query — DOM lookup, matching, classification, query diagnostics (no presentation, no raises)
                 ▼
Html / LazyHTML

In particular, Query should not depend on Query.LabelError; presentation belongs above the query boundary.

Target contract

Use one result envelope for all public Query operations, with a structured, data-only failure. A struct makes accidental tuple-pattern coupling less likely; tagged maps/tuples would also work if kept consistent.

defmodule PhoenixTest.Query.Failure do
  @enforce_keys [:kind, :query]
  defstruct [:kind, :query, :candidates, :labels, :inputs, :cause]
end

@type result(value) ::
        {:ok, value} |
        {:error, %PhoenixTest.Query.Failure{}}

kind should distinguish at least :not_found, :ambiguous, :no_label, :missing_for, :missing_input, :mismatched_id, :conflicting_label_association, :invalid_argument, :invalid_selector, and :invalid_html. query contains the requested selector/text/label/position; candidate HTML and label/input evidence remain raw data, not formatted strings.

Important: failure normalization must retain the current diagnostic payload. A plain {:error, :not_found} would force callers to query again or degrade existing messages.

Required changes by layer

1. Query becomes the total lookup boundary

  • Replace heterogeneous return values from find, find_first, find_one_of, label, selected, role, and ancestor finders with the common envelope.
  • Remove/move all find!, find_one_of!, find_by_label!, find_by_role!, and find_ancestor! raisers from Query. The inline conflict raise in determine_implicit_or_explicit_label/3 must instead return :conflicting_label_association.
  • Normalize Query-owned lookup and association failures (including unsupported :at values in filter_by_position/2) rather than allowing Query’s own control-flow/pattern-match errors. LazyHTML parser and selector exceptions are explicitly out of scope and may continue to raise.
  • Handle all find_one_of/2 outcomes in label association; find_associated_input/4 currently lacks a {:found_many, _} branch.
  • Escape selector values used to resolve for/aria-labelledby IDs, or return an invalid-selector failure rather than leaking the parser exception.

2. Add caller-owned composition

  • Create an action-facing adapter (likely shared by Live and Static) that maps Query.Failure to the current ArgumentError wording. This replaces Query.LabelError and Query's inline message functions.
  • Convert Element builders to non-bang find functions returning {:ok, struct} / {:error, failure}. Their existing bang names can be temporarily retained above this level as compatibility adapters, but they cannot call Query bang APIs.
  • Live and Static should call these functional element/query operations, add operation-specific context if desired, then raise at their public action boundary. This provides identical base diagnostics without coupling Query to a session implementation.
  • Assertions should translate the same failure into ExUnit.AssertionError. This fixes the current unhandled :mismatched_id label tuple in assertion pattern matching.

3. Replace the internal API directly

Query is internal, so its existing result shapes and ! functions can be replaced directly. The compatibility boundary is the public Live/Static behavior: preserve their exception types and messages unless a deliberate user-facing improvement is made.

Migration plan

  1. Characterize the public boundary: capture Live/Static action failures and assertion behavior for selector, text, selected, label, ARIA, role, one-of, ancestor, and position queries. These are the compatibility tests that matter.
  2. Introduce failure data: add Query.Failure and convert Query operations to return it, with no formatting and no explicit raises. Convert the conflicting-label case into a failure value. LazyHTML parser/selector exceptions may continue to propagate.
  3. Move formatting upward: preserve current ArgumentError messages using a caller-side action formatter; provide a separate assertion formatter.
  4. Migrate Elements, then Live and Static: make each compose functional results. Migrate both session types together to avoid divergent public diagnostics.
  5. Migrate Assertions and remove Query bang APIs: use failure data rather than positional tuple matching, retain count behavior, then delete the legacy Query ! functions.

Regression coverage required

Existing tests already pin many ArgumentError messages in test/phoenix_test/query_test.exs (notably lines 26–70, 233–308, 376–681, and 873–992). Keep those as adapter/integration expectations during migration, and add functional-result tests for every failure kind.

  • Non-bang label query with an implicit and explicit association pointing to different inputs: must return an error, never raise.
  • Query-owned invalid position and malformed one-of input: each returns a typed failure. Do not add an expectation that invalid selectors or malformed HTML are caught—LazyHTML may raise for those.
  • Duplicate associated inputs: verify it cannot become a CaseClauseError.
  • Live and Static missing/ambiguous links, buttons, fields, selects, parent forms, and nested LiveView scopes: verify exception type plus key candidate diagnostics.
  • Assertion/refutation label mismatched-ID and ambiguity paths: verify AssertionError, never a pattern-match exception.

Key risks / decisions

Compatibility: Query is internal. Its API can change directly; preserve the user-visible Live and Static behavior covered by their tests.
  • Define “no explicit Query raises” precisely. Remove Query’s ! functions and Query-authored raise calls. LazyHTML selector/parser exceptions may propagate; do not rescue them merely to satisfy this refactor.
  • Do not collapse ambiguity into absence. Actions and assertions need candidates to explain both differently.
  • Do not put messages in failure data. Data enables Live/Static/action/assertion-specific wording and localization later; one shared formatter can still keep generic diagnostics consistent.
  • Preserve lookup semantics. The refactor must not alter exact matching, candidate ordering, ARIA fallback, :at, or uniqueness rules. Note that find_first/4 currently does not apply :at, unlike find/4; decide whether that is an intentional behavior to preserve or a separately-scoped bug fix.
